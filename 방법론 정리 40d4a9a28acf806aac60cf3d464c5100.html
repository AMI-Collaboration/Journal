CDA 방법론 정리 — Graph-based Plan Alignment 개편안

한 줄 요약

각 로봇이 분산적으로 협업을 제안하고 YES/NO로 응답하며, Graph LLM이 계획 그래프를 제약된 편집 연산으로 정렬하면서 목표 달성 여부까지 판정한다. 룰은 형식과 구조적 무결성만 검증한다. 해결되지 않은 부분은 강제로 배정하지 않고 사용자에게 보고한다.

0. 설계 원칙

원칙의미
Allocation-free중앙 배정자 없이, 제공자가 동의(YES)한 협업만 실행된다.
LLM decides, rules verify의미 판단(문제 식별, 편집, 실행 가능성, 목표 커버리지)은 모두 LLM이 한다. 룰은 형식 검사, 그래프 구성, 구조 검증, 연쇄 정리, 스케줄링만 담당한다. 단어·유사도 기반의 의미 판단 룰은 두지 않는다.
No silent failure실행 불가능하거나 커버되지 않은 목표는 원인과 함께 명시적으로 보고한다.
One-way pipeline단계 간 피드백 루프 없이 단방향으로 진행한다. 단계 안에서 로봇이 자기 출력의 형식 오류를 1회 스스로 고치는 것은 허용한다 (단계 간 피드백은 Limitation / Future work).

역할 분담

주체담당
로봇 VLM (분산)Offer 선언, Local Plan 생성, 협업 제안에 대한 YES/NO 응답
Graph LLM (중앙, 1회 호출)문제 식별, 편집 시퀀스 Δ, 목표 커버리지 판정, 미해결 원인 분류
룰 (결정론적)Stage 2·3 형식 검사, 그래프 구성, 편집의 구조적 허용성 검사, 엣지 확정, 의존성 연쇄 정리, 스케줄링, 리포트 확정

1. 문제 설정 (Problem Setting)

  • 이종 로봇 집합 R = {r₁, …, r_N}, 공통 자연어 지시 I
  • 각 로봇 rᵢ는 자신만의 관측 oᵢ(이미지)를 가지며, 관측 범위(obs_scope)는 공유하지 않는다 → 부분 관측(partial observability)
  • 목표: 중앙 배정 없이 실행 가능한 Joint Plan을 생성하고, 달성하지 못한 목표는 원인과 함께 Report로 반환

2. 파이프라인 개요

Stage이름주체입력 → 출력
1Offer Generation각 로봇 (VLM)oᵢ, I → Offer Oᵢ
2Local Plan Generation각 로봇 (VLM) + 형식 검사(룰)Oᵢ, {Oⱼ} → Local Plan Pᵢ
3Edge Proposal각 로봇 (VLM) + 형식 검사(룰)공개된 요청·제안 → YES/NO 응답 → 후보 협업 엣지 + 동의 라벨
4Graph-based Plan AlignmentGraph LLM + 룰계획 그래프 G → Joint Plan, Provenance, Report

3. Stage 1–3: 분산 제안 단계

Stage 1. Offer Generation

각 로봇이 자신의 이미지와 지시를 보고 Offer를 선언하고 브로드캐스트한다.

Oᵢ = ⟨Cᵢ, Aᵢ⁺, Aᵢ⁻, Hᵢ, Nᵢ, Gᵢ⟩

기호필드설명공개
Cᵢcapability로봇의 능력 (이동, 조작 등)O
Aᵢ⁺can_do수행 가능한 행동 (번호가 붙은 목록)O
Aᵢ⁻cannot_do수행 불가능한 행동과 이유O
Hᵢhas_items보유 물품 (이미지에서 직접 보이는 것만)O
Nᵢneed_from_others타 로봇에게 필요한 것 (기능 단위로 서술)O
Gᵢintends수행하려는 하위 목표 (번호가 붙은 목록, 예: "할머니께 따뜻한 차 준비") → Stage 2의 serves, Stage 4.2 커버리지 판정의 기준O
  • obs_scope는 공유하지 않는다.
  • Gᵢ는 step 순서가 아니라 하위 목표이다. 구체적인 step은 Stage 2에서 작성한다.

Stage 2. Local Plan Generation

각 로봇이 step 시퀀스 Pᵢ를 생성한다. 이 단계에서 작성하는 step 타입은 τ ∈ {LOCAL, ASK_HELP, RECEIVE, PASS} 이다. HELP는 Stage 3에서 요청에 YES로 응답할 때만 생성된다.

타입의미쌍
LOCAL단독 수행—
ASK_HELP ↔ HELP능력 부족으로 인한 협업요청 ↔ 제공 (HELP는 Stage 3)
RECEIVE ↔ PASS물품 전달로 인한 협업수령 ↔ 전달

step 필드

필드대상설명
usesLOCAL근거가 되는 자기 can_do 번호
targetASK_HELP, RECEIVE, PASS상대 로봇. 구속력 없는 힌트 ("이 로봇이 해줬으면")
itemRECEIVE, PASS물품 이름
enablesASK_HELP (필수), RECEIVE (선택)이 요청이 필요한 자기 뒤쪽 LOCAL step 번호 → 4.4 연쇄 정리에 사용
serves모든 step이 step이 기여하는 자기 Gᵢ 번호
  • 제공 측도 PASS를 먼저 제안(offer)할 수 있다.
  • 물품 운반 담당은 확정하지 않는다. 이동 가능한 쪽이 운반한다 (이동 가능한 giver가 가져다주고, 아니면 이동 가능한 receiver가 가지러 감).

형식 검사 (룰): 번호·목록이 맞는지만 확인한다.

  • step 타입이 허용된 값인지
  • target이 존재하는 다른 로봇인지
  • uses / enables / serves가 존재하는 번호인지
  • PASS 물품이 자기 Hᵢ에 있는지, RECEIVE 물품이 target의 Hᵢ에 있는지
  • 둘 다 이동 불가능한 로봇끼리 물품을 주고받으려 하지 않는지
  • LOCAL의 위치가 자기 공간인지

형식 오류가 있으면 오류 목록과 함께 1회만 로봇이 스스로 다시 작성한다. 그래도 남은 형식 오류 step은 브로드캐스트 전에 제외하고 Provenance에 기록한다.

단어나 유사도로 의미를 판단하는 검사(비물리적 행동, 관찰 행동, 선행 step 누락, 무거운 물건 등)는 두지 않는다. 의미상 문제가 있는 step은 Stage 4.2에서 Graph LLM이 식별해 DROP한다.

Stage 3. Edge Proposal

Stage 2의 요청(ASK_HELP, RECEIVE)과 PASS 제안을 모든 로봇에게 공개하고, 각 로봇이 병렬로 응답한다. 요청과 제안을 구분하지 않고 하나의 응답 형식을 쓴다.

필드설명
answerYES (하겠다 / 받겠다) 또는 NO
reason짧은 이유 (NO일 때 4.2 원인 분류의 근거)
existing_step(선택) 이미 자기 플랜에 같은 일이 있으면 그 step ID
  • YES 시 처리 (코드):
    • 요청에 YES → 자기 플랜에 HELP / PASS step을 추가하고, 요청 ID로 짝을 기록 (텍스트 비교 없음). existing_step이 있으면 새 step 없이 그 step을 연결
    • PASS 제안에 YES → RECEIVE step 추가. 로봇이 그 물품을 쓰는 행동을 함께 적었으면 사용 step도 추가하고, 적지 않았으면 RECEIVE만 추가 (고정 문장으로 채우지 않음)
  • NO 시 처리: 엣지를 만들지 않고, 이유를 해당 요청 노드에 기록한다.
  • 같은 물품을 여러 로봇이 요청해도 모두 후보로 넘긴다. 누구에게 줄지는 4.2 SELECT에서 정한다.

동의 라벨 κ(e) — 엣지는 제공 측이 YES 한 경우에만 생기며, 코드가 라벨을 붙인다.

κ(e)조건
mutual상대가 나를 지목했거나 나에게 제안했고, 내가 YES 함
provider-only지목받지 않았는데 자원함, 또는 PASS를 제안했는데 받는 쪽이 응답하지 않거나 NO 함
  • 후보 엣지가 하나도 없는 요청은 엣지 라벨이 아니라 요청 노드의 상태("후보 없음") 로 표시한다.

형식 검사 (룰): can_do 번호가 맞는지, 자기 Hᵢ에 있는 물품인지, 이동 불가능한 로봇이 다른 공간으로 도우러 가려는지, 이동 불가능한 로봇끼리 물품을 주고받는지만 확인한다. 통과하지 못한 YES는 엣지를 만들지 않고 이유와 함께 기록한다. 유사도 기반 검사는 두지 않는다.

4. Stage 4: Graph-based Plan Alignment

4.1 Plan Graph Construction (룰)

G = (V, E_seq ∪ E_col, κ)

  • V: 모든 로봇의 step
  • E_seq: 로봇 내부 순서 엣지 (Stage 2·3 순서 그대로)
  • E_col: 협업 엣지 (TRANSFER, HELP). 모두 제공 측이 YES 한 엣지
  • 상태 라벨만 부착:
    • 엣지: κ
    • 요청 노드: 후보 수, "후보 없음", NO 응답과 이유
    • 사이클에 속한 노드 표시
  • 이 단계에서는 어떤 것도 확정하지 않는다.

4.2 Constrained Graph Editing & Coverage Judgment (Graph LLM, 1회 호출)

LLM이 issue 목록이 아닌 그래프 전체와 모든 Offer를 보고, 다음 두 가지를 한 번에 출력한다.

(1) 편집 시퀀스 Δ = (δ₁, …, δ_k)

연산설명
SELECT후보 중 provider 선택 또는 교체 (같은 물품을 여러 요청이 원하는 경우 누구에게 줄지 포함)
MERGE이미 다른 엣지로 충족된 요청을 그 엣지에 연결해 해결 처리. 제공자의 step은 바꾸지 않고, 해결 표시와 선후관계만 추가
DROP불필요·중복·실행 불가능한 step 제거 (자기 Offer와 모순되는 step, 사이클을 끊기 위한 제거 포함)
ORDER로봇 간 선후관계 추가 (로봇 내부 순서는 바꾸지 않음)

각 편집에는 짧은 근거(rationale)를 함께 출력한다 → Provenance에 기록.

(2) 목표 커버리지 판정 C

각 Gᵢ에 대해 다음을 출력한다.

  • 상태: covered / partial / uncovered
  • 근거 노드(evidence): 이 목표를 커버하는 노드 ID 목록
  • 커버되지 않은 경우의 원인: No volunteer / Capability gap / Left unresolved (요청 노드의 NO 이유를 근거로 판단)

구조적 제약 (by construction): 금지하는 게 아니라 애초에 표현할 수 없게 설계한다.

  • 연산은 기존 노드 ID만 참조 → 새 step 생성 불가
  • SELECT의 선택지는 제공 측이 YES 한 엣지(κ ∈ {mutual, provider-only}) 로 한정 → 동의하지 않은 로봇에게 배정 불가
  • SELECT는 양 끝 노드가 모두 존재하는 엣지에만 적용 가능. provider-only 엣지에서 받는 쪽 노드가 없으면, LLM은 받는 쪽의 기존 step(그 물품·도움이 필요한 step)에 연결할 수 있다. 연결할 노드가 없으면 그 제공 step은 4.4에서 정리된다.

판단이 애매한 부분은 편집하지 않고 미해결(Left unresolved)로 남긴다.

프롬프트 구성

구성내용
역할배정자가 아니라 이미 제안된 계획을 정렬하는 역할임을 명시 (새 일 생성·비동의 로봇 배정 금지)
입력노드 목록(ID / 로봇 / 타입 / 내용 / serves / 상태 라벨), 엣지 목록(ID / 종류 / 양 끝 노드 / κ), 모든 로봇의 Offer
연산·제약위의 4개 연산 정의와 구조적 제약, "애매하면 편집하지 말 것"
판단 관점미해결 요청, 중복 작업, 경쟁하는 후보, 자기 Offer와 모순되는 step, 로봇 간 순서가 필요한 곳, 사이클 (issue 목록이 아니라 살펴볼 관점만 제시)
출력JSON (edits, coverage). 편집은 SELECT/MERGE → DROP → ORDER 순서로 출력
  • CoT와 few-shot 예시는 사용하지 않는다. 판단 근거는 rationale 필드로만 남긴다.
  • 형식 오류를 줄이기 위해 JSON 스키마를 필드 단위로 명시하고, API의 structured output(JSON 모드)을 사용한다.

4.3 Structural Admissibility Check & Edge Finalization (룰)

(1) 허용성 검사: 편집을 출력 순서대로 적용하며, 구조적 무결성을 깨는 편집은 적용하지 않고 이유와 함께 기록한다.

  • 검사 항목 (구조만):
    • 존재하지 않는 ID 참조 (앞선 편집으로 DROP된 노드 포함)
    • SELECT 대상이 제공 측이 YES 한 엣지가 아님, 또는 양 끝 노드가 없음
    • ORDER가 같은 로봇 내부 순서를 건드림
    • 편집 적용 후 새로운 사이클 발생
  • capability·보유 물품 같은 의미적 일치는 검사하지 않는다 (4.2에서 LLM이 판단).
  • 재시도 없음 (one-way): 거절된 편집은 Report의 Rejected edits로 전달.

(2) 엣지 확정 (기본 정책): 편집 적용이 끝난 뒤, 각 요청에 대해 실행할 협업 엣지를 다음 규칙으로 확정한다.

경우처리
SELECT로 선택된 엣지실행
편집이 없고, mutual이며 후보가 하나뿐인 엣지그대로 유지 (실행)
편집이 없고, provider-only이거나 후보가 여럿인 경우실행하지 않음 → 해당 요청은 미해결
후보 없는 요청실행하지 않음 → 해당 요청은 미해결
  • 양쪽이 모두 동의한 엣지만 기본으로 채택하는 것이므로, 룰이 판단하는 것이 아니라 동의를 존중하는 것이다. LLM은 DROP이나 SELECT 교체로 이를 바꿀 수 있다.

(3) 불변식 확인: I1(동의), DAG 여부를 마지막에 확인한다. 위반이 있으면 파이프라인을 멈추지 않고 해당 부분을 Report에 기록한다.

4.4 Dependency Closure (룰)

DROP되었거나 미해결인 step에 의존하는 step을 연쇄적으로 정리한다.

  • 실패한 요청(ASK_HELP, RECEIVE) → 그 요청이 enables 하는 step → 그 step에 의존하는 다른 로봇의 step 순으로 전파
  • 예: 해결되지 않은 RECEIVE 뒤의 내려놓기, DROP된 PASS 앞의 집기
  • 4.2 이후에도 남아 있는 사이클은 사이클에 속한 step을 정리한다.
  • 정리된 step은 Provenance에 “closure로 제거”로 기록한다.

4.5 Scheduling (룰)

  • 요청 대기 위치 조정: 요청 step을 그것이 enables 하는 step 바로 앞으로 옮긴다. 할 일의 내용과 의존 관계는 그대로이고, 로봇이 불필요하게 기다리지 않도록 대기 위치만 조정한다. 사이클이 생기면 되돌린다.
  • step 길이: 타입별 기본값을 쓴다. HELP, 그리고 이동이 필요한 PASS/RECEIVE는 "보통", 나머지는 "짧음". ASK_HELP는 대기이므로 길이가 없다. (추가 LLM 호출 없음)
  • 위상 정렬 순서로 시작·종료 시점을 계산하고, 시간 슬롯 Δt = 5분 단위로 배정한다.

4.6 Report Finalization (룰)

4.2의 커버리지 판정 C를 받아서 구조적으로만 보정하고 최종 Report를 만든다. LLM의 판정을 새로 뒤집는 의미 판단은 하지 않는다.

  • 근거 누락: covered/partial로 판정했는데 evidence가 비어 있으면 → Left unresolved로 처리한다.
  • 무효화: covered/partial로 판정된 목표의 evidence 노드가 4.3 거절, 4.3 엣지 미확정, 4.4 정리로 사라졌으면 → Infeasible로 낮춘다.
  • 데드라인 검사: 스케줄 결과가 시간 제약을 넘으면 → Deadline exceeded로 기록한다.

5. 불변식 (Invariants)

불변식내용보장 방식
I1 동의 (Consent)실행되는 모든 협업 엣지는 제공자의 동의(YES)가 있고, 모든 step에는 이를 생성한 로봇이 존재한다Stage 3에서 YES 한 경우에만 엣지 생성, 4.2에서 구조적으로 보장, 4.3에서 재확인 (기본 채택도 mutual만)
I2 목표 보존 (Goal Coverage)모든 Gᵢ가 최종 계획의 step으로 커버된다4.2에서 LLM이 판정, 4.6에서 구조적으로 보정 후 보고 (보장이 아니라 판정·보고이며, 실제 커버 여부는 평가 지표 TF로 외부 검증)
I3 실행 가능성 (Feasibility)순서 그래프는 DAG, 각 step은 능력·보유 물품과 일치, 시간 제약 충족DAG: 4.3에서 검사 후 거부, 남은 사이클은 4.4에서 정리 / 형식상 일치(번호·물품 목록): Stage 2·3에서 룰이 검사 / 의미상 일치: 4.2에서 LLM이 판단 / 시간: 4.6에서 판정 후 보고
